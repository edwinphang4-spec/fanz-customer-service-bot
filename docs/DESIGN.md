# 客服 Bot 设计原则

> 这份文档不是说明书，是**判断依据**。
> 以后要加任何规则、话术、能力，先对照这里 —— 判断该不该加、加在哪一层。
>
> 为什么需要它：这套系统前两个月是**事故驱动**长出来的（30 次急救叠加），
> 每条规则单独看都对，并排看全是同一个隐含假设。2026-08-13 走查发现，
> 客户问打折、问赔偿、发一张无关照片，bot 三次都回"风扇有什么问题？我帮你安排"——
> 而他从头到尾没说过风扇坏了。根因不是某条脚本写坏了，是**从来没有一个整体标准**。

---

## 一、四条原则（Edwin 2026-08-13 定）

### 1. 红线只管边界，不管内容

红线保证"绝对不能说的"（折扣金额、赔偿承诺、保修结论、时限承诺），
**其余交给模型看着上下文说**。

> 红线是一堵墙，不是一条轨道 —— 它划定不许越过的边界，不规定在墙内往哪走。

**由来**：旧设计里命中红线 = 整条回复由代码写死，连"这句话之后聊什么"也一并
决定了。于是六条脚本各自长出一条"我帮你安排"的尾巴，替客户决定了他为什么来。
红线只需要管"不许谈折扣金额"，不该管下一句。

### 2. 不预设客户为什么来

任何路径都不许默认"你是来修风扇的"。包括：脚本尾巴、注入历史的 system note、
报修流程的触发条件、照片的处理方式。

**由来**：六条固定话术里四条以报修收尾，加上 system note 里那句
`Continue helping with the fan issue`，把整段对话锁死在一条轨道上。

### 3. 已经花钱得到的信息不许丢

视觉识别、查库、计算的结果**必须用上**。不能查完了还发预设话术。

**由来**：客户发了一张无关照片，系统真的调了视觉模型（花了钱），
模型答"这不是发票"，代码把结果扔掉，发了固定的"照片收到啦，讲一下是什么问题"。
从客户角度，跟没看一模一样。

### 4. 能力长了，规则要跟着长

加新能力时，**回头检查旧规则该不该改**。用下面第五节的检查清单。

**由来**：视觉识别 2026-07-09 就有了，但"每张图都是发票"这条假设停在原地，
一个月没人回头看。代码层一直在长，脚本层停着不动。

## 二、三段式架构

**代码决定"发生什么"，模型决定"怎么说"。**

```
客户消息
   │
① 事实层（代码）—— 只产出事实和约束，不产出话
   │   查库 / 视觉识别 / 保修计算 / 复发判定 / 钱意图识别
   │   → 该落库的立刻落库（escalation / 工单 / 埋点）★ 副作用永远确定
   │   → 生成本轮【事实卡】+【本轮禁令】
   ▼
② 表达层（模型）—— 看着事实卡说人话
   │   静态提示词（短）+ 事实卡（动态，不相关就不出现）+ 对话历史
   ▼
③ 出站验证层（代码）—— 说错了不放行
   │   金额 / 保修结论 / 时限承诺 / 空头承诺 / IC
   │   两次不过 → 落回固定脚本（= 旧行为，这是兜底）
   ▼
 发送
```

**这个设计能成立的原因**：最坏情况等于旧设计。我们没有拆掉安全网，
是在网上面加了一层更好的第一次尝试。

**不许交给模型的**（副作用，永远在代码里）：
escalation 记录、工单落库、保修计算、品牌推断、日期换算、埋点。

---

## 三、红线清单（唯一权威，其他地方不许再写一遍）

| # | 绝不能 | 出站怎么验 |
|---|---|---|
| R1 | 报标准费率表以外的任何金额 | 钱意图激活时，扫回复里的金额 |
| R2 | 确认/否认/讨论折扣 | 词表 + 入站意图 |
| R3 | 谈赔偿、退款、责任归属 | 词表（最严的一条） |
| R4 | 自己下保修结论（系统没算过时） | 扫"在保/过保/免费"类表述 |
| R5 | 承诺具体时限（"24小时内""明天给你答复"） | `TIME_PROMISE` 运行时检查 |
| R6 | 承诺自己做不到的后续动作 | 空头承诺检查 |
| R7 | 确认/暗示具体上门时间 | 提示词 + 人工抽查 |
| R8 | 发师傅的身份证号 | `detectICLeak`（遮蔽不拦截） |
| R9 | 不知道品牌时说马达保修年限 | `calcWarrantyStatus` 拒绝判定 |

**R5 的话术随能力变**：工单通知群没建好之前，事实卡写
`No human is notified in real time`；建好之后改成
`An operator group is notified immediately` —— **同一个位置，一个配置切换，
话术自动变真**。能力和话术从此绑在一起，不会再出现"能力没了话术还在吹"。

## 四、事实卡格式

每轮由代码按需注入，不相关就不出现。

```
[FACTS — this turn]
· Customer raised: <意图，如 pricing/discount>
· System action taken: <代码已经做了什么，如 escalation recorded>
· Known: <查到的事实，如 brand=fanz, purchase_date=2020-05-18>
· Intake progress: <已收集 / 还缺什么>
· Constraints this turn: <本轮禁令>
· Do NOT assume why the customer is here. Nothing in this conversation says
  they have a faulty fan. Respond to what they actually said.
```

最后一条**每张卡都带**（原则 2 的强制落地）。

**情境规则住在产生它的代码旁边，不住在静态提示词里。**
旧设计里"催单怎么办"写在提示词第 7 条，而代码在 LLM 之前就截走了 ——
那条规则永远执行不到，还占着篇幅。规则跟着代码走，加能力时**必然**会看到它。

## 五、加新能力时的检查清单（原则 4 的落地）

每次加能力，逐条过：

- [ ] 这个能力产生的信息，**有没有被用上**？还是查完就扔？（原则 3）
- [ ] 它会不会让某条**旧规则过时**？（例：加了视觉分类 → "照片都是发票"作废）
- [ ] 它会不会让某条**旧话术变成谎话**？（例：通知群建好前不许说"马上联系你"）
- [ ] 新写的话术**结尾**有没有预设客户来意？（原则 2）
- [ ] 它涉及红线吗？涉及就**只加约束，不写死整条回复**（原则 1）
- [ ] 副作用（落库/埋点）是不是在**代码**里，不依赖模型？
- [ ] 静态提示词有没有因此可以**删掉**几行？（只增不减 = 三个月后没人读）

## 六、能力边界（做得到 / 做不到，都要说清楚）

| 能做 | 边界 |
|---|---|
| 报修受理 | 只收集，**不许确认上门时间**（看不到师傅排班） |
| 保修判定 | 代码算，带"以最新官方政策为准 / 师傅上门确认"免责 |
| 发票识别 | 读型号和日期，**人工核实为准**；不存发票地址（隐私） |
| 产品咨询 | 讲规格、比较、房间适配；**不许报价**（销售团队报） |
| 通用问题 | 保养、清洁、安装环境；**涉电气安全一律建议持证师傅** |
| 轻量自助排查 | 见下 |
| 闲聊 | 一两句，然后**开放式**拉回（不是拉回报修） |

### 轻量自助排查（批次三）

**不做完整的排查知识库** —— 那种手册在师傅脑子里不在文件里，
现在去问 Fanz 会卡住。只做三条不用问任何人的通用常识：

| 症状 | 顺口问一句 |
|---|---|
| 遥控没反应 | 方便的话先试试换个遥控电池？有时候是这个 |
| 完全不转 | 电闸有没有跳？墙上开关是开着的吗？ |
| 遥控失灵 | 要不要试试重新配对？ |

**铁律：不强求、不挡流程。** 客户说试过了、或懒得试，**照常开单**。
零成本、零风险，可能省下一趟上门费。

## 七、留的口子

### 工单通知卡片要留"实际原因"回填入口

师傅处理完在群里回一句：**电池 / 跳闸 / 真的坏了 / 其他**。

跑几个月就是一份**我们自己积累的**真实排查数据，比问客户要手册准得多 ——
到那时再决定要不要把上面那张表扩成真正的排查树。

设计通知卡片时**把这个位置留出来**（不用一开始就做完整）。

### 售前意向没有落点

产品咨询问完就没了 —— 跟"工单没人接"是同一个病：
**系统知道有个潜在客户，但没人会知道**。要真有商业价值，
需要一张意向记录表（型号、房间、联系方式）。批次三跟通知群一起做。

## 八、历史教训（为什么有些东西长这样）

- **钱红线三层重复是故意的**（提示词 + 代码 + 脚本）：纵深防御，代码漏了提示词兜底。
  但"不许说时限""不许说让我查"的重复是**焦虑式堆叠** —— 出事就再加一句，
  没人回头合并。加规则前先搜一下是不是已经有了。
- **例句会被当模板抄**（marketing 那边踩过四次：钩子、CTA、Merdeka 日期）。
  提示词例句里**不许出现日期、型号、数字**。
- **"推了 master" ≠ "线上在跑"**：用行为探针确认。CS bot 最便宜的探针是
  问一句"可以打折吗"，看回复是"尽快"（新）还是"24小时内"（旧）。
- **测试要能变红才有意义**：改完做反向验证（故意破坏，确认真的红）。
